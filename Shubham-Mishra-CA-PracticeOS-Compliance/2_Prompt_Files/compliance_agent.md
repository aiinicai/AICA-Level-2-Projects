# Agent 3 — Compliance Checklist Agent — Prompt (HEADLINE FEATURE)

**Model:** `claude-sonnet-5`

This is the product's core value: it checks a drafted professional document against a
mandatory-clause checklist for its document type, and reports exactly what's missing.
Per CLAUDE.md this agent must never be simplified under time pressure.

## Checklist source

Mandatory clauses are defined per document type in `src/agents/compliance.py::CHECKLISTS`,
derived from the actual document templates already generated by the L1 app
(`CA_PracticeOS_Compliance.html`: `generateEngagement()`, `generateNW()`,
`generateCertificate()`, `generateRep()`, `generateWP()`, `generateFeeNote()`), plus the
explicit example CLAUDE.md gives: "engagement letters must state scope, fees,
responsibilities, limitations."

This is deliberately a *different* checklist from the L1 app's existing `checklistData`
object (Net Worth Certificate, Statutory Audit, Tax Audit, ...) — that one is a
procedural audit-workflow checklist ("bank statements obtained", "UDIN tracked"). Agent 3's
checklist instead asks: **does the drafted document's text actually contain each
required clause?**

## System / task prompt (per checklist item, batched in one call)

```
You are a compliance reviewer for an Indian chartered accountancy firm. You will be
given the full text of a drafted {doc_type} and a list of mandatory clauses that this
document type must contain. For EACH clause, decide whether the document's text
satisfies it.

Mandatory clauses to check:
{numbered list of clause name + description}

Return ONLY a JSON array, one object per clause, in the same order given, with keys:
{
  "id": string,          // the clause id as given
  "present": boolean,    // true only if the document text actually contains this clause
  "evidence": string,    // a short quote (<=25 words) from the document proving it's
                          // present, or "" if not present
  "reason": string       // one sentence: why present, or what specifically is missing
}

Be strict: a clause is only "present" if its substance is actually in the text, not
merely implied. Do not be fooled by section headings alone — check the content under
the heading actually satisfies the clause's description.
```

Tested 2026-09-21 against a deliberately vague fee clause ("Professional fees: to be
mutually agreed between the parties in writing prior to commencement" — no amount,
rate, or basis stated): the model correctly marks Fees as **absent**, reasoning that
deferring the fee to a future agreement doesn't state a basis (fixed/hourly/percentage)
the way SA 210 expects an engagement letter to. An earlier draft of this prompt
suggested a vague fee mention should still count as "present" — that was too lenient
and has been removed; the stricter behavior matches real audit engagement letter
standards better.

## Agentic loop (perceive → reason → act → validate)

1. **Perceive** (`::perceive`) — load the document (plain text, or HTML from Agent 2,
   tags stripped), and classify its document type: first by matching a title line
   against known document type names, falling back to an LLM classification call
   only if no title match is found.
2. **Reason** (`::reason`) — one Claude call per document, checking all mandatory
   clauses for that document type at once (cheaper and more consistent than one call
   per clause), returns per-clause present/absent + evidence + reason.
3. **Self-check / validate** (`::self_check`) — a keyword-heuristic pass cross-checks
   each LLM verdict, but deliberately only in one direction: if the LLM says a clause
   is present but none of that clause's trigger keywords appear anywhere in the text,
   the item is downgraded to `needs_review` instead of being trusted outright — a
   strong, reliable signal of hallucination. It does **not** second-guess an "absent"
   verdict the same way, because judging whether a clause's substance is genuinely
   missing (versus a placeholder like "[To be filled]" sitting under an on-topic
   heading) requires the same semantic judgment the keyword check can't make; a blank
   Net Worth Certificate template still contains the words "Assets" and "Liabilities"
   in its column headers, so a symmetric check would flag every blank template as
   "needs review" instead of cleanly absent. This is the genuine self-checking step —
   it catches potential over-claiming rather than one-shot-trusting the model's
   output, without manufacturing false uncertainty about genuinely missing content.
4. **Act** (`::run`) — compiles the final report: overall verdict (PASS only if every
   clause is `present` and none need review), the list of missing clauses, and the
   list of clauses flagged for human review.

## Why this design

- **Batched single call per document** — checking clauses independently in separate
  calls would be more expensive and could reason inconsistently about the same text;
  one call sees the whole document and returns a structured verdict per clause.
- **Evidence quotes** — force the model to point at the actual text it's basing each
  verdict on, which is auditable by the reviewing CA and harder to hallucinate past.
- **Keyword self-check as a cheap, deterministic second opinion** — a compliance tool
  that can silently mark a missing clause as present is worse than useless; the
  self-check step is what makes this a validating agent rather than a single LLM call
  with a JSON wrapper.
