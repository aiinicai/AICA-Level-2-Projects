SYSTEM CONTEXT
You are an expert full-stack app developer building a web application for a Chartered Accountant who is a first-time developer. Before writing any code, think step by step through the plan below, state your plan briefly, and only then generate the app. Prioritize a clean, simple, form-driven UI over cleverness — the end user is a CA and audit staff, not engineers.
STEP 1 — UNDERSTAND THE PURPOSE
Build a web app called "Audit Observation Tracker" used by a CA firm to log, track, and report observations raised during different types of audits: Stock Audit, Tax Audit, CAG Audit, Concurrent Audit, and allow adding new audit types later without code changes (keep this as a configurable dropdown list, not hardcoded).
The app has two logical parts:
Engagement/Client master — one record per audit assignment.
Observation log — many observations per engagement, each with its own lifecycle (raised → discussed → rectified/closed).
STEP 2 — DEFINE THE DATA MODEL (think through this before coding)
Engagement (Audit Assignment) record:
Engagement ID (auto-generated, unique)
Client Name
Client PAN/GSTIN (optional text field)
Audit Type (dropdown: Stock Audit / Tax Audit / CAG Audit / Concurrent Audit / Other — editable list)
Financial Year / Period of Audit
Audit Team Members (multi-select or comma-tagged list of names)
Engagement Partner
Audit Start Date / Audit End Date
Branch/Location (optional, useful for CAG/Concurrent/Stock audits with multiple branches)
Overall Status (Planning / In Progress / Fieldwork Complete / Report Issued / Closed)
Observation record (linked to one Engagement):
Observation Reference No. (auto-generated, unique, format like <AuditTypeCode>-<FY>-<ClientCode>-<Sequence>, e.g. SA-2526-ABC-001)
Linked Engagement (dropdown of existing engagements)
Date of Observation
Area/Process (e.g., Inventory Valuation, GST Input Credit, Fixed Assets — free text or dropdown)
Observation Description (long text)
Severity Level (dropdown: Critical / High / Medium / Low — color-coded: red/orange/yellow/green)
Financial Impact / Amount Involved (optional numeric field, currency ₹)
Root Cause (optional text)
Recommendation (text)
Discussion Stakeholder(s) — name(s) and designation of client-side person(s) the observation was discussed with
Date of Discussion
Management Response / Comments (text)
Status (dropdown: Open / Under Discussion / Management Response Awaited / Rectified / Closed / Not Accepted)
Rectification Status (dropdown: Not Started / In Progress / Rectified / Not Rectified / Not Applicable)
Target Rectification Date
Actual Rectification Date
Person Responsible (audit team member who owns follow-up)
Attachments (optional — allow file name/reference text if actual file upload isn't feasible in AI Studio's environment)
Remarks/Follow-up Notes
STEP 3 — CORE FEATURES
Dashboard/Home screen: summary cards showing total observations, open vs closed, count by severity, count by audit type; a table of the most recent/high-severity open observations.
Engagement management: add/edit/view engagements; list view with search and filter by audit type, year, client, status.
Observation management:
Add new observation (form with all fields above; reference no. auto-generated on save, non-editable)
Edit existing observation (status/rectification updates over time)
View all observations in a filterable, sortable table: filter by Client, Audit Type, Financial Year, Severity, Status, Rectification Status, Discussion Stakeholder, Date range
Search by keyword across description/area
Export/Download:
Export a single observation as a formatted PDF and as a Word (.docx) document (letterhead-style, one observation per page, with all fields laid out clearly — reference no., client, area, description, severity, status, etc.)
Export all observations for one engagement (combined) as PDF, Word, and Excel
Export filtered results (whatever filters are currently applied on the table) as Excel (.xlsx) with one row per observation and all fields as columns
Excel export should also include a summary tab (counts by severity/status)
Basic validation: mandatory fields (Client, Audit Type, Financial Year, Observation Description, Severity, Status) enforced before save; reference numbers must never duplicate.
Simple, non-technical UI: use plain labels (not jargon), color-coded severity tags, status badges, and a left-side navigation with just 3–4 sections (Dashboard, Engagements, Observations, Reports/Export). Assume the user has never coded before — no exposed technical settings, no raw JSON views.
