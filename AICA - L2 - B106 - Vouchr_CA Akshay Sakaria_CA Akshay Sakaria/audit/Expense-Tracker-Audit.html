The product has useful breadth, but its financial and security core is unfinished

This is a substantial, thoughtfully structured prototype of a CA-firm expense and accounts-payable companion. It should not yet hold production client books or be represented as a Zoho/Odoo/QuickBooks-class accounting system.

CriticalA01 · Architecture · Confirmed by code trace

Live configuration still runs demo identity and browser-only financial state

backend.ts creates a Supabase client, but StoreProvider always loads DEMO_USERS, DEMO_CLIENTS and localStorage. Login always presents role buttons. Financial actions call setS rather than Supabase reads/RPCs. main.tsx only prevents startup when configuration is missing; adding configuration passes that guard without adding real authentication or persistence.

Recommended change. Implement a real Auth/session/profile bootstrap and a server-backed repository. Route every financial mutation through explicit commands/RPCs. CriticalA02 · Security · Reproduced in isolated PostgreSQL

Financial and document views bypass tenant RLS

expense_register, payment_register, orphan_documents and tds_liability are created without security_invoker. Under the representative authenticated grants used by the project tests, Tenant A sees zero Tenant B expense rows directly but reads Vendor B and its ₹1,000 bill through expense_register. CriticalA03 · Security · Reproduced in isolated PostgreSQL

Disabled users bypass RPC tenant checks through SQL NULL

app_role()/app_client() return NULL for an inactive profile. can_see_client() then returns NULL. record_payment uses IF NOT can_see_client(...) rather than rejecting anything other than TRUE. In PL/pgSQL, IF NULL does not enter the rejection branch. An inactive Tenant A user successfully created a payment in Tenant B. save_bill_document and apply_advance have the same fail-open pattern.

Why it matters. Deactivation does not reliably revoke financial write access. The service/NULL conflation in several guards also treats absent application roles as trusted service activity.

Recommended change. Require a non-null authenticated UID and an active profile at every public RPC entry. Use can_see_client(...) IS NOT TRUE to reject. Identify privileged service calls from a trusted database/JWT role, never COALESCE(app_role(), service). Centralize and test authorization.

Done when. Inactive, missing-profile, expired-session and cross-client calls fail before any write or external action. Preserve a test specifically for NULL authorization results.

HighA05 · Security · Collision reproduced; authorization confirmed by source

Drive folder authorization and names do not isolate clients

drive-upload verifies access to clientId but accepts any folder beginning Vouchr/ without ..; it does not bind the folder to that client. Folder identity elsewhere is a sanitized display name truncated to 40 characters. Distinct Hindi names both become file, and punctuation/truncation can collide. drive-share grants access to the same name-based folder.

Why it matters. Client documents may be filed into another client’s shared tree, or two clients can unintentionally share a folder. A rename can create a new tree and strand earlier records. This risk exists independently of database RLS.

Recommended change. Use immutable client UUIDs and stored Drive folder IDs. Derive the destination entirely on the server from clientId, validated FY and document kind. Add a unique mapping and an explicit rename operation that changes labels while preserving identity.

Done when. Two identical/Unicode client names produce different folder IDs; forged folder paths cannot redirect uploads; renaming preserves access to historical files.

Foreign keys do not enforce matching client ownership

Tenant A could insert a bill referencing Tenant B’s vendor, create a payment using Tenant B’s bank account, and attach Tenant B’s document. Foreign keys check that UUIDs exist, but not that their client_id matches the parent. Similar checks are missing for cost centres, linked bank sources, linked notes and reversal references.

Why it matters. Financial relationships can cross client boundaries, misroute accounting and undermine authorization checks that assume connected records belong to the same tenant. UUID unpredictability is not an ownership control.

Month locks and fiscal close can be bypassed

The expense trigger checks the new month only. A submitted October bill was moved into November after October was locked. An admin deleted a payment from a locked month. Vendor-note cancellation explicitly bypasses its locked-month check. A client admin inserted a fiscal_years row already marked closed because the close guard covers UPDATE only.

Why it matters. A locked period can change without an unlock/reopen trail. Closed-year indicators can be forged, and financial close totals cannot be trusted as a stable snapshot.

External writes and message retries have no durable idempotency boundary

WhatsApp checks whether wamid exists before processing but inserts that ID only after upload/bill creation. Parallel deliveries can both pass. TDS thresholds aggregate the wrong economic events

prepare aggregates all non-rejected bills for a vendor, including drafts, later invoices and other TDS categories. Effective-dated rates cannot be versioned reliably

tds_rates uses code as its sole primary key, and updateTdsRate replaces an entry by code.
